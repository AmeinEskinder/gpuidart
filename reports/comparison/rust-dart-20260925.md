# Rust and Dart measurements, 2026-09-25

Completed three alternating repetitions of all four workloads in Rust and Dart, for **24 foreground runs**. A later series with a corrected input cutoff completed 12 runs before two focus interruptions stopped it. The series remain separate.

The repeated idle samples show a memory premium for the complete Dart build. CPU ranges overlap, and these results do not establish lower Dart overhead. Both implementations use the same GPUI Kit table with 100,000 records. This comparison does not isolate Dart VM memory from application data, the adapter or other differences between the builds.

## Missing-update investigation

The original [49-of-50 observation](paired-20260925-0/rust-cell/failure.json) remains an unresolved correctness observation. It happened in the Rust reference. Its native click callback calls `edit` directly, which synchronously increments the update counter and writes the cell. The report contains 49 updates, 49 written cells and `Tick 000049` in native state. **Source inspection localizes the missing invocation between successful input injection and entry into that Rust handler.** It does not identify which click disappeared or establish a driver, Windows or GPUI fault. No focus exception was recorded in that attempt.

Diagnostic builds now tag each injected click and record these stages:

1. The driver records the sequence and the number of packets accepted by `SendInput`.
2. GPUI records mouse down/up positions and entry into the native click handler.
3. Rust or Dart records entry into the application handler.
4. Rust records application of the update. Dart also records its acknowledgement, linked by dataset revision.
5. The fixture reads the resulting price. Dart checks both its own value and the native cell through the existing diagnostic API.

Four diagnostic runs completed **700 of 700 full event chains**: 50 cell clicks and 300 burst clicks in each implementation. No driver deadlines were skipped. All sequences reached the native handler, application handler, native update and expected row-zero state. These runs add instrumentation and readbacks, so they are excluded from performance comparisons. See the [trace reports](trace-pair-1).

Trace setup also retained two attempts that could not acquire foreground focus before input, in [trace-original-1](trace-original-1) and [trace-original-2](trace-original-2). Preliminary logging checks applied 50 and 10 clicks successfully, but their 64-bit tags returned only the low 32 bits on this machine. Those checks remain in [trace-original-3](trace-original-3) and [trace-tags-1](trace-tags-1). The final tracing uses a 32-bit tag and verifies every sequence.

The original failure did not recur in those traces or in the completed repeated runs. Its cause remains unresolved. Successful repetitions do not remove it from the reliability record.

## Method and retained observations

Each run used a fresh release process, a three-second warmup and a ten-second workload. Repetition order was Rust/Dart, Dart/Rust, then Rust/Dart. Within each implementation, workloads were idle, scroll, cell and burst. The viewport was 860 by 650 logical pixels at window DPI 120. The machine used the Balanced power plan. Background desktop activity and processor frequency were not isolated. The rendering adapter was not recorded.

The tables below describe the complete `paired-traced-20260925` series. Despite its directory name, **input tracing was disabled** in these performance runs. The name records that they followed the trace investigation. Binary and driver hashes are in [paired-session.json](paired-session.json); toolchain and dependency versions remain those in [artifacts.json](artifacts.json). The [machine inventory](measurement-environment.json) records the CPU, display and graphics drivers.

| --- | ---: | ---: | ---: | --- |
| Original failed cell pilot | 1 failed correctness check | 50 / 49 | Not retained by the old failure report | Unresolved loss before Rust handler entry |
| Correlated diagnostic runs | 4 | 700 / 700 | 0 | All event chains and state readbacks complete |
| Complete repeated series | 24 | 2,101 / 2,101 | 1 | One extra cell click at the measurement cutoff |
| Follow-up after cutoff fix | 12 | 1,050 / 1,050 | 3 | Two additional idle attempts interrupted by focus loss; series incomplete |

In the complete repeated series, Rust's first scroll run received 599 events; the other scroll runs received 600. Rust's cell runs received 50 clicks each. Dart's first cell run received 51, and its other cell runs received 50. Every burst run received 300 clicks and wrote 2,400 cells. Native scroll displacement matched the delivered wheel count in every completed run.

The extra click was scheduled at 10,000 ms, and the driver recorded elapsed time of 10,000.0028 ms before calling the injection code. The loop had checked the duration just before crossing that boundary. The driver now checks elapsed time again and caps the schedule with an integer slot count. That explains the extra input in this run; it does not explain the original missing update. The follow-up has no extra inputs.

The first series has 22 observations eligible for an equal-work timing subset. The Rust scroll run with a skip and the Dart cell run with an extra input remain in the descriptive tables and reliability totals. Completed correctness failures now retain process measurements and an explicit failed `correctness` result. Interrupted attempts also remain in analysis output. The suite does not silently keep only successful runs.

The two 50-cell runs each transferred 7,524 bytes and touched 50 native records. Each burst run transferred 165,578 bytes and touched 2,400 records. Initial dataset upload is separate. None of these measurements establishes input-to-present latency.
