# Input to display, Dart and Flutter Windows (2026-09-29)

The exit table's last row waited two days on the right to start an ETW
trace. With the account in Performance Log Users, PresentMon 2.6.0 runs
from a normal session and this series fills the row as far as a capture
without elevation can: for every click and wheel event the driver
injects, how long until the fixture presents the next frame, on both
fixtures over the cell, burst and scroll workloads, and how long until
that frame reaches the display where the capture follows it there, which
it does for the Flutter fixture and for a few percent of the Dart
fixture's frames.

## Method

`run.ps1 -CapturePresent` starts PresentMon beside the fixture and keeps
the records of the fixture's process. Three things had to change for that
to work from a session without elevation:

- Each run gets its own ETW session name. The runner named every session
  after its own process ID, so the eighteen runs of the first series
  collided on one session, recorded nothing and left an orphan behind
  ([present-20260929-0](present-20260929-0) keeps six of those runs,
  complete and verified, without a capture).
- The capture takes every process and the runner reduces the file to the
  fixture's process afterwards (`present-filter.json` keeps the counts of
  what was dropped). PresentMon names the fixtures from this session, but
  when it followed them by name it lost part of the Dart fixture's
  presents in five runs of nine (13 presents for 50 clicks in one), while
  the unfiltered capture kept them all.
- The analyzers read PresentMon 2.6's columns (`MsUntilDisplayed` where
  earlier releases wrote `DisplayedTime` and `DisplayLatency`).

Two limits of a capture without elevation showed in the records
themselves. The GPUI fixture presents through a flip-model composition
swap chain (`Composed: Flip`) and PresentMon follows almost none of its
presents to the display: `MsUntilDisplayed` is empty for all but a few
percent of them. PresentMon warns at start that without elevation it
cannot query processes of another account, and the step from a
flip-model present to the display runs through the desktop compositor,
which is one; that this is the cause is an inference from the two, not a
measurement. The Flutter fixture
presents through a copy-model swap chain (`Composed: Copy with GPU GDI`)
and is followed. And PresentMon's own input association
(`MsAllInputToPhotonLatency`, `MsClickToPhotonLatency`) is empty for both
fixtures.

So the figure reported for both fixtures is computed on one clock from
what each side does record: **input to present** runs from the driver's
QPC timestamp, taken before it injects the click or wheel packet, to the
start of the first `Present` call the fixture makes after the injection
completed (`TimeInQPC` of PresentMon's record). **Input to display** adds
PresentMon's `MsUntilDisplayed` where it is known. The first present
after an input is the response frame when the response is synchronous; a
pressed or hover frame can precede it, as the
[benchmark notes](../../benchmarks/README.md) say. In the cell workload
both fixtures present once per click, so there it is the response frame.

The Dart fixture runs with `deferDatasets` and `retainRecords: false`, the
SDK's mode for large datasets; the Flutter fixture is the one of the
earlier series with its button ripple off. 100,000 records, ten seconds
after the warmup, three repetitions of each workload per fixture in each
of two series, unattended with the display held awake:
[present-20260929b-0](present-20260929b-0) to [-2](present-20260929b-2),
captured for every process, and [present-20260929c-0](present-20260929c-0)
to [-2](present-20260929c-2), followed by name. A run counts when it is
an equal-work run (every injected input delivered, no driver deadline
missed, verification passed) and its capture answers at least 98 percent
of its inputs: 21 of the 36. The unfiltered capture cost the driver
deadlines in six runs of series b; the capture by name lost presents of
the Dart fixture in five runs of series c.

Both fixtures answer an input with a present within one frame interval at
the median and within two at the 95th percentile. The median itself says
little beyond that: it is the distance from the driver's schedule to the
next frame, which depends on the phase between the two and ranges over
most of a frame interval from run to run on either fixture. The tails
differ where the work differs. A scroll is answered alike. A click on the
Dart fixture reaches the second frame more often than on the Flutter
fixture (95th percentile 33 to 34 ms against 20 to 27): the click crosses
to the Dart isolate and the edit comes back before native applies it,
where Flutter's handler runs on the thread that builds the frame.

presented at the display rate (597 presents for 300 clicks) and the

## What an elevated session would add

The display half for the Dart fixture. With elevation PresentMon can
attribute the compositor's events and follow flip-model presents to the
display, and its own input association fills in for both fixtures. The
harness needs no change for it: the same command from an elevated
terminal produces the same files with those columns filled.

## Limits

One machine, one day. Two to six runs per cell of the table, because a
run had to be both an equal-work run and completely captured. Input to
present is measured to the start of the present call, not to the
display; the input timestamp is the driver's, taken before the
injection, so it includes the injection itself (about 0.01 ms). The
first present after an input is not proven to contain the change outside
the cell workload. The traced diagnostic build's changed-frame
correlation (`input-analysis.json`) is a separate measurement and is not
reported here.
