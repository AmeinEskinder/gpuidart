# Sort, filter and group over a million records, Dart and Flutter (2026-09-29)

The comparison series so far measured idle, scrolling and cell edits over
100,000 records. This series measures the operations a data table exists
for, at the row cap: a descending sort on the price column, that sort with a
filter keeping about half the records, and both with a grouping by a
twelve-value sector column with a count, an average and a maximum per group.

## Method

`run.ps1` gained a `view` workload: one click per second on the first button,
which both fixtures turn into a view cycle when `GPUIDART_BENCH_WORKLOAD` is
`view`. Each click moves the table to the next of four stages, sort,
sort+filter, sort+filter+group and the plain records again, so a twelve-second
run walks the cycle three times. Both fixtures add a fourth 200-pixel
`Sector` column (`Sector 0` to `Sector 11`) for the grouping and keep the
geometry of the earlier series otherwise. The runner verifies that the
reported stage equals the click count modulo four and that no record
changed.

The Dart fixture republishes its table with the next `UiTableView` and times
the click handler through the rebuild acknowledgement, which native sends
after it has recomputed the view over the dataset and notified the table; the
frame that shows the result follows. The Flutter fixture computes the stage
on the UI isolate in the click handler, as an application sorting its own
list does: an index sort on prices parsed once at startup, a filter over that
order, and a grouping that emits a header row per sector with its count,
average and maximum; it times the handler through the post-frame callback of
the frame that shows the result (build, layout and paint done, raster
pending) and reports the handler's own computation and that frame's
`FrameTiming` span beside it. Neither figure is a presentation time; both end
one frame before it.

Three runs per fixture, alternating, 1,000,000 records, twelve seconds after
the three-second warmup, one machine in one hour: [view-1m-20260929-0](view-1m-20260929-0)
to [-2](view-1m-20260929-2). Every run delivered its twelve clicks with no
missed driver deadline and passed verification. A second series that would
have recorded the samples in click order was interrupted at its first run
when another application took the foreground while the machine was in use;
its failure record is retained in [view-1m-20260929b-0](view-1m-20260929b-0).
The fixtures now report samples in click order for the next series; the runs
below report them sorted, so a stage is named only where the gaps between
samples leave no doubt.

The Dart samples fall into two bands in every run: six between 105 and

Over the whole cycle the Dart fixture's view changes complete in about half
the time of the Flutter fixture's: medians of 146 to 178 ms against 315 to
366 ms, a ratio of 1.8 to 2.5 across the three runs. That is not the order
of magnitude the exit condition asked for. The grouped stage is the slowest
on both sides and the largest share of the Dart figure; the section below
on the sort explains where the native time went and what changed.

the records exist because it builds them before opening.

## The sort that was not a sort

The fixtures' prices rise with the row index (`100 + i / 100`), so the
descending sort above only had to reverse one already-ordered run, and both
sides finished it in about the time of a linear pass. A native probe
(`view_recompute_at_1m_records_is_measured`, an ignored test run explicitly
in release) times the three stages over the same million records with the
prices permuted (`100 + ((i * 7919) mod 1,000,000) / 100`, the same values in
scrambled order). With the view code as this series ran it, the native sort
took 5.4 to 7.5 s, the sort with the filter 3.0 to 3.6 s and the grouped
stage 3.0 to 3.8 s: the comparator parsed both cells on every comparison,
about forty million parses for a million records.

Two changes to the view computation followed. Every sorted, compared or
aggregated column is now parsed once per recompute, a single numeric sort
key sorts the parsed keys beside their row indices, and a group's aggregates
fold in one pass as its records are collected, sharing the sort's parses.
The probe after the changes, three runs per stage:

| Stage | Before, ms | After, ms |
| --- | ---: | ---: |
| Sort, 1,000,000 records | 5,357 to 7,539 | 149 to 164 |
| Sort + filter, 499,999 records | 3,004 to 3,592 | 148 to 184 |
| Sort + filter + group, 500,011 rows | 3,039 to 3,850 | 403 to 549 |

The grouped stage's remainder over the filtered sort is the walk over half a
million records in sorted order, each reaching its sector cell and price at
random addresses. The fixtures now permute their prices in the view
workload; the series above is the ordered-price case and the next series
measures the permuted one.

## Limits

Sorted samples, so the Flutter stages are not separated and the Dart ones
are separated by their gaps rather than recorded; the next series records
click order. One machine, one hour, three runs each, no presentation
capture. The Flutter implementation is one reasonable in-isolate design,
not the fastest possible: an application could sort in an isolate or keep a
sorted index; the Dart figure includes a description rebuild and one
acknowledgement round trip that a native application would not pay. The
Flutter fixture parses prices once at startup where the Kit table parses at
each recompute.
